# Runner proxy와 WASM 직결 성능 비교

[직결 구현 PR #15](https://github.com/lesomnus/wafl/pull/15)의 성능을 같은 runner release
바이너리로 비교했다. 같은 WASM 앱 두 개에 합계 500 req/s를 보낼 때 proxy → direct 전환으로
서버 CPU 중앙값이 **21.78% → 7.99%, 63.3% 감소**했다. 부하 중 PSS는 **31.92 → 32.19 MiB**로
비슷했다. 작은 HTTP 응답에서는 runner의 중계·요청 관리 경로를 제거한 효과가 크게 나타났다.

**Traefik을 포함한 CPU 합계는 52.67% → 59.06%로 오히려 12.1% 증가했다.** 이 게스트는
응답마다 TCP 연결을 닫는다. 전체 경로의 효율은 gateway와 앱의 연결 재사용 조건까지
포함해 평가해야 하며, runner 프로세스 CPU만으로 플랫폼 전체의 절감률을 계산하면 안 된다.

## 서버만 비교

각 셀은 새 프로세스로 실행한 **3회 측정의 중앙값**이다. **CPU 100% = 코어 1개**다.
CPU·메모리는 두 앱을 실행하는 서버 PID 전체의 합계이며 부하 생성기·측정기는 제외한다.
`http` 구간은 500 req/s, `work` 구간은 요청마다 xorshift 200,000회를 수행하며 200 req/s다.

| 지표 | Wasmtime CLI × 2 | Runner proxy × 1 | Runner direct × 1 |
| --- | ---: | ---: | ---: |
| HTTP CPU | 11.69% | 21.78% | 7.99% |
| HTTP 요청당 CPU | 0.234 ms | 0.436 ms | 0.160 ms |
| HTTP 부하 중 PSS | 43.16 MiB | 31.92 MiB | 32.19 MiB |
| HTTP 응답 지연 p95 | 1.12 ms | 1.11 ms | 0.82 ms |
| 유휴 PSS | 43.16 MiB | 31.99 MiB | 32.31 MiB |
| 연산 응답 CPU | 15.49% | 21.79% | 14.40% |
| 연산 요청당 CPU | 0.775 ms | 1.090 ms | 0.720 ms |

직결의 HTTP 요청당 CPU는 proxy보다 **0.276 ms 적었다**. 연산을 추가한 응답에서는
CPU 감소율이 **33.9%**였다. 앱 연산이 차지하는 비중에 따라 상대 개선 폭이 달라진다.
이 차이는 forwarding·admission·request lifecycle을 포함한 경로 전체의 차이다.
함수별 profiling으로 TCP forwarding 하나의 비용을 분리한 값은 아니다.

HTTP CPU의 3회 범위는 CLI **10.29–11.89%**, proxy **19.79–24.19%**, direct **7.30–8.39%**였다.
HTTP p95 범위는 각각 **0.78–1.69 ms**, **0.91–1.42 ms**, **0.65–0.82 ms**다.
공유 호스트의 변동이 있으므로 CLI와 proxy의 p95처럼 작은 중앙값 차이를 순위로 해석하지 않는다.
CLI는 같은 Wasmtime 버전이지만 host feature/executor가 다르며 두 프로세스다.
주된 비교는 **동일한 runner 바이너리의 proxy/direct 설정 차이**다.

## Traefik까지 포함한 전체 경로

Traefik 3.8.0 file provider의 두 Host route를 사용했다. proxy 경로에는 `wafl-instance`
헤더를 주입하고, direct 경로에는 공개된 실제 WASM 주소를 backend로 넣었다.

```text
proxy:  클라이언트 → Traefik → runner HTTP ingress → WASM
direct: 클라이언트 → Traefik → WASM
```

같은 게스트 두 개, HTTP 합계 500 req/s, 각 3회 중앙값이다.

| 지표 | Traefik + proxy | Traefik + direct |
| --- | ---: | ---: |
| Runner CPU | 22.69% | 9.99% |
| Traefik CPU | 29.98% | 49.06% |
| **CPU 합계** | **52.67%** | **59.06%** |
| 합계 요청당 CPU | 1.054 ms | 1.182 ms |
| 부하 중 합계 PSS | 152.90 MiB | 152.43 MiB |
| 응답 지연 p95 | 2.46 ms | 2.13 ms |
| 연산 응답 CPU 합계, 200 req/s | 36.39% | 38.29% |

CPU 합계 범위는 proxy **50.67–53.11%**, direct **56.46–64.66%**로 세 번 모두 직결이 높았다.
p95 범위는 **2.00–2.87 ms**, **2.03–2.71 ms**로 겹친다. 이 실험에서는 runner에서 줄인 CPU보다
Traefik에서 증가한 CPU가 더 컸고, 메모리 합계는 비슷했다.

게스트가 `Connection: close`로 응답하므로 직결에서는 Traefik이 매번 새 upstream 연결을
열어야 한다. 기존 [runner proxy](../../src/proxy.rs)는 이 hop-by-hop 헤더를 제거하고 자신의
HTTP ingress 연결을 유지할 수 있다. 따라서 Traefik→runner 구간에는 connection pooling이
가능하고, runner→WASM의 새 TCP 연결은 runner가 생성한다. 이 경로 차이는 별도 진단으로
확인했다. [100 req/s·2초 진단](2026-11-25-direct-connections.json)의 HTTP 200개 요청 동안
gateway backend에 새로 관찰한 TCP 주소 쌍은 **proxy 0개, direct 200개**였다. proxy에서
관찰된 주소 쌍 3개에는 변화가 없었다. `/proc/net/tcp`의 ESTABLISHED·TIME_WAIT 등을 비교한 값으로,
주소 쌍 재사용·만료로 누락될 수 있어 정확한 connect syscall 횟수와 같지는 않다.
이 진단의 CPU 값은 성능 표에 섞지 않았으며, connect/parse/GC 각각의 비용을 함수별
profiler로 분리한 결과는 아니다.

## 측정 환경과 한계

- Linux x86-64, AMD Ryzen 7 5825U. cgroup CPU 4개 상당, memory 8 GiB. 공유 호스트, affinity 미고정.
- runner 구현은 `b07dd01547107a164e9f00195394b3ef0522d917`, release build, Rust 1.100.0.
  측정 스크립트는 `bd23615`이며 제품 코드는 위 runner 구현과 같다.
- Wasmtime 51.0.0. 공식 CLI는 on-demand allocator·disk cache off·parallel compilation off로 설정했다.
  runner와 CLI의 한도는 인스턴스당 linear memory 64 MiB, resource table 1,024개다. CPU/fuel quota 없음.
- 게스트 SHA-256은 `794f7c95d4091e27041ceb67c607958f02f89870a6bbf1b3bbe4205c248b94f7`로 이전 비교와 동일하다.
  두 앱은 동일 코드를 공유하고 별도 큰 heap을 할당하지 않는다. stack·기본 heap은 사용한다.
- 프로세스마다 Tokio/Rayon worker 2개, Traefik GOMAXPROCS 2. OTLP·DB·per-request 앱 로그 없음.
- 준비 후 2초 안정화, idle 10초, HTTP 10초, work 10초. 부하 앞에 각각 2초 warmup.
  각 조건을 3회 반복하고 실행 순서를 회전했다. 빌드와 측정은 겹치지 않았다.
- 모든 네트워크는 loopback이다. 클라이언트는 **요청마다 새 TCP 연결**을 사용하고 게스트는
  응답마다 연결을 닫는다. Traefik→runner 구간의 연결 재사용은 위와 같다. keep-alive를 지원하는
  게스트, HTTP/2/gRPC, TLS, 큰 응답, 실제 Pod 간 네트워크, 최대 처리량·cold start는 측정하지 않았다.
- PSS는 공유 페이지를 나눠 계산한 process resident memory다. file cache·kernel socket buffer 등
  전체 cgroup 사용량은 포함하지 않는다. 두 앱에서의 공유 효과를 다수 앱의 밀도로 외삽하지 않는다.

최종 측정은 backend 9회·gateway 포함 6회, 측정 구간 요청 **105,000개·실패 0개**다.
HTTP 실제 처리율은 **499.61–499.89 req/s**, 요청 생성 지연 p95는 **1.06–1.12 ms 수준**이었다.
측정 구간에 cgroup CPU throttling은 없었다. 이 환경의 latency 변동 범위도 함께 보존한다.

## 요청 생성 지연과 재측정

처음 실행한 동기 `/proc` 표본 수집 방식에서는 CLI 일부 반복의 요청 생성 지연 p95가
209 ms·1,942 ms로 커지고 실제 처리율이 약 490·476 req/s로 떨어졌다. 그 구간은 일정한
500 req/s의 응답 지연 비교에 적합하지 않아 최종 표에서 **첫 실행 전체를 제외**했다.

메모리 표본 수집을 별도 thread로 분리하고 CPU/time 구간 경계도 별도 counter로 잡은 뒤
모든 구성을 다시 측정했다. 이 변경은 측정기만 변경하며 runner·Wasmtime·WASM 바이너리는
그대로 사용했다. kernel memory accounting 지연이 요청 생성 event loop를 막을 가능성을
제거한 것으로, 최초 지연 원인 전체를 확정하는 profiler 분석은 아니다.

[첫 backend 실행 원본](2026-11-25-direct-preliminary-backend.json)과
[중단한 첫 gateway 실행 원본](2026-11-25-direct-preliminary-gateway.json)도 보존한다.
유리한 반복만 골라 최종 결과에 섞지 않았다. 최초 측정기 소스는 `206a718`에서 확인할 수 있다.
